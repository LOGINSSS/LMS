## 1. 背景与动机

### 1.1 0.1 基线盘点（现状）

| 域 | 0.1 现状 | 0.2 缺口 |
|---|---|---|
| 课程 | `course` 表只有 name/cover/intro/category/status；详情 = 卡片信息 + 课次 + 点赞 | **没有课程内容**：无目录、无章节、无正文、无考题归属、无发布编排 |
| 选课 | `course_enrollment` 直接插入（`POST /courses/{id}/enroll`），无门槛 | **没有抢课窗口/库存**：无抢课发布时间、无库存概念、无高峰削峰 |
| 考题 | `question` + `question_biz`（biz_id 绑定，但**无 biz_type 区分业务类型**） | 课程与考题的归属关系未定义清楚 |
| Redis | 仅网关 JWT 黑名单、auth token、lms-ai 会话消息 —— **用量很少** | 课程详情/学情/用户信息无缓存；无实时榜 |
| 积分 | `points_record` 流水 + SQL SUM 聚合榜单；签到 `sign_in` 全局每日一次 | 无课程维度积分、无实时榜（ZSET）、签到与课程页无绑定、无日期边界业务 |
| AI | lms-ai 个人 Agent + 学习评测管道（diagnose→plan→exercise→assess） | 管道工具面窄；**前端无 AI 入口**；无 Text-to-SQL |
| 知识库 | `knowledge_base` 支持 owner_type=1（课程）/2（用户），课程库已可用 | 课程创建未自动建库；**Python 端对接未打通**（标记 TODO）；封面图等上传链路未接入课程表单 |

### 1.2 0.2 目标（需求原文提炼）

1. **课程内容化**：建新表存放课程内容——目录结构 + 章节 markdown 正文；考题归属到课程（复用 exam 模块）。
2. **课程发布**：老师编辑完内容后发布；学生端/老师端课程详情页展示**两栏大纲**（左：可滚动章节大纲；右：点击章节看 markdown 片段）。
3. **抢课环节**：课程有抢课开始/结束时间；抢课用 **Redis 预检库存 + Kafka 异步落库**。
4. **Redis 体系化**：课程详情、学情详情、个人基本信息做缓存；课程详情右侧**实时积分排名**用 **ZSET**；大纲阅读、考试、签到都能获得积分，签到在课程页进行，需判断日期（今天/下一天）。
5. **AI 管道工具扩展**：学习评测管道有更多可用工具可调。
6. **课程知识库**：每门课对应自己的知识库，对接 Python 端（**标记待实现**），文件上传链路先行（含课程封面图）。
7. **抢课模块化**：抢课独立成模块（解耦）。
8. **AI 入口 + Text-to-SQL**：前端接入 AI 对话入口；为「AI 创建课程/分析课程/解答问题/联系老师」的终极目标设计 Text-to-SQL 能力。

### 1.3 关键设计决策速览（先回答设计问题）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 考题设计成存在 exam 模块与课程对应，还是怎么设计？ | **考题留在 lms-exam**（题目是题库资产，类型/难度/解析/答案都在那里），通过 `question_biz` 绑定课程/章节，**给 question_biz 增加 `biz_type`**（1 课程 / 2 章节 / 3 考试卷）以区分绑定语义；课程侧经 Feign 聚合，不复制题目数据 |
| Q2 | 课程整篇 MD 存 MySQL 会不会不好？ | **按章节粒度存 MySQL 完全没问题**：章节树（结构化）落 `course_catalog`，每章 markdown 正文落 `course_chapter`（LONGTEXT，单章通常几 KB~几十 KB）；**不要**整篇塞一个大字段（不利于局部更新/缓存/权限/增量渲染）。大体积附件（图片/视频/文档）走 lms-media，全文检索将来可进 ES，向量化进 lms-kb |
| Q3 | 两栏大纲（左大纲右 markdown 片段）是不是好存 MySQL 一点？ | **是的**：左栏 = `course_catalog` 章节树查询（轻量、可滚动、可高亮）；右栏 = 按 chapterId 单查 `course_chapter` 正文。天然符合「大纲轻查询 + 正文按需加载」，也是拥有者（老师）与学生的共用视图 |
| Q4 | 抢课怎么设计？ | 独立模块 **lms-grab**：`course` 增加 `grab_start_time`/`grab_end_time`/`stock`；抢课走 **Redis Lua 原子预检库存**（窗口 + 去重 + 扣减），成功后发 **Kafka 消息异步落库** `course_enrollment`；失败/超时回补库存 |
| Q5 | 签到日期业务？ | 签到改为**课程维度**（`sign_in` 增加 `course_id`，uk 变 `(user_id, course_id, sign_date)`），Redis 存上次签到日期，判断「今天已签/昨天连续/更早重新开始」，支持连续签到天数 |
| Q6 | 实时积分排名？ | 每门课一个 **ZSET** `course:points:{courseId}`（member=userId, score=积分），课程详情右侧 `ZREVRANGE` 取 TopN；发放积分时 ZINCRBY + 落库流水 |
| Q7 | AI 管道工具扩展？ | learning-agent/course-agent 工具面扩展：目录阅读、章节内容、签到、积分榜、抢课状态、课程考题等 |
| Q8 | 前端 AI 入口？ | lms-web 增加全局聊天浮窗 + 课程页 AI 面板，接 `/agent/chat`；Text-to-SQL 作为 lms-ai 的只读查询工具设计 |

## 3. 课程内容域设计（lms-course 扩展）

### 3.1 课程内容建模：目录 + 章节正文

课程是一个**立体内容实体**，分两层建模：

- **目录结构（course_catalog）**：章节树（章/节两级，`parent_id` 挂父子），轻量、可滚动大纲、可排序；
- **章节正文（course_chapter）**：每章一段 markdown（LONGTEXT），支持行内图片（url 指向 lms-media）。

```
course（原表，扩展抢课/发布字段）
 └── course_catalog  （章节树：course_id + parent_id + name + sort + level）
      └── course_chapter（章节正文：catalog_id + course_id + content_md + word_count）
```

> 设计取舍：目录与正文**分表**——大纲页只查 catalog（不拖大字段），正文页按 chapterId 单查；正文支持缓存（`chapter:content:{id}`），局部更新只动一章。

### 3.2 MD 文档存储决策（回答 Q2）

| 方案 | 结论 |
|---|---|
| 整篇课程存一个大字段（如 `course.content LONGTEXT`） | ❌ 不推荐：无法局部更新、缓存粒度差、大纲与正文耦合、权限控制难 |
| **目录表 + 章节正文表（每章一行 LONGTEXT）** | ✅ 推荐：单章 markdown 通常几 KB~几十 KB，MySQL 完全承载；左栏大纲右栏正文天然匹配；缓存/增量/权限都好做 |
| 大文件（图片/视频/PDF 课件） | 走 **lms-media**（存储抽象本地磁盘→可换 OSS），内容里只存 url |
| 全文检索 / 语义检索 | 全文检索进 ES（lms-search 已有 course 索引可扩展出 content 字段）；语义检索走 **lms-kb**（课程知识库，owner_type=1 已就绪） |

> **结论**：markdown 正文按章节粒度存 MySQL 是**合适的**；「整个长文一个 blob」才是问题，我们不做。课程整体导出（如 AI 生成全文）可由 catalog+chapter 拼接而来。

### 3.3 考题归属设计（回答 Q1）

**原则：题目永远留在 lms-exam，课程只「引用」，不「复制」。**

- `question`（题库资产：题型/难度/答案/解析）不动；
- `question_biz` 增加 **`biz_type`**（TINYINT）：`1=课程` / `2=章节` / `3=考试卷`，配合既有 `biz_id`：
  - 课程级考题：`biz_type=1, biz_id=courseId`（课程详情页「课程测验」）
  - 章节级练习：`biz_type=2, biz_id=catalogId`（每章学完可做「本章练习」）
  - 考试卷：`biz_type=3, biz_id=paperId`（0.3 组卷预留）
- 唯一键调整：`uk(question_id, biz_type, biz_id)`（原 uk_question_biz 需随迁移重建）；
- 接口：`GET /questions/biz/{bizType}/{bizId}` 已存在，扩展按 biz_type 过滤；新增 `GET /courses/{id}/questions`（Feign 聚合 course+exam）。

### 3.4 课程发布流程（老师端）

发布状态机（`CourseStatus` 从 2 态扩展为 5 态）：

```
0 草稿(DRAFT) ──编辑内容──▶ 1 待发布(PENDING_GRAB) ──到 grab_start_time──▶ 2 抢课中(GRABBING)
   ▲                            │                                              │
   └── 下架(OFFLINE) ◀──────────┴──────── 到 grab_end_time ──▶ 3 进行中(ONGOING)
                                                               │
                                                               └── 结课 ──▶ 4 已结束(FINISHED)
```

- 老师流程：建课（草稿）→ 编辑目录/章节正文/关联考题 → 设置抢课时间与库存 → 提交发布（待发布）→ 系统按时间自动流转；
- 状态流转由 **定时任务（@Scheduled 或 lms-ai task 体系）** 扫描 `grab_start_time`/`grab_end_time` 驱动；
- `0 下架` 保留为终态回退（任意态可下架）。
- 发布时（进入 PENDING_GRAB 或首次预热时）由 lms-course **通知 lms-grab 预热库存**（见 §4）。

- 拥有者视角（老师）：可增删改章节、编辑 markdown、关联章节考题、预览发布效果；

## 4. 抢课模块设计（lms-grab 新增）

### 4.1 为什么独立成模块（回答「抢课解耦」）

抢课是**高峰、高并发、强一致诉求**的业务，与常规课程 CRUD 的节奏完全不同：

1. **流量隔离**：抢课峰值打 Redis（毫秒级），不压 lms-course 的 MySQL；
2. **技术栈独立**：Lua 脚本 / 分布式锁 / Kafka 生产者集中在 lms-grab，课程模块只做消费落库；
3. **可替换性**：未来换秒杀中间件 / 改规则，只动 lms-grab；
4. **演进空间**：抢课可扩展「预约提醒、候补队列、限购规则」而不污染课程模块。

### 4.2 数据模型（lms_grab 库）

| 表 | 字段要点 |
|---|---|
| `grab_record` | id、course_id、user_id、grab_time、source（1 抢课）、status（1 成功待落库 / 2 已落库 / 3 已回补）、幂等键 uk(course_id, user_id) |
| （扩展 course） | `stock`（总名额）、`grab_start_time`、`grab_end_time`（在 lms_course.course 上） |

### 4.3 抢课主流程（Redis 预检库存 + Kafka 异步落库）

```
学生 POST /grab/{courseId}（lms-grab）
  │
  ▼
① 窗口判断：now ∈ [grab_start_time, grab_end_time]？  ← Redis `grab:window:{courseId}`（发布时写入）
  │
  ▼
② Lua 原子脚本（单次往返，防超卖/防重复）：
   - 去重：SISMEMBER grab:users:{courseId} user → 已抢则返回 DUP
   - 扣库存：DECR grab:stock:{courseId} → <0 则 INCR 回补并返回 SOLD_OUT
   - 记录：SADD grab:users:{courseId} user；HSET grab:detail:{courseId} user timestamp
  │
  ▼
③ 成功 → 发 Kafka topic `grab-success`（key=courseId, value={courseId,userId,grabTime}）
  │
  ▼
④ lms-course 消费端异步落库：
   - 幂等：uk_course_student（course_enrollment 已有）→ 已存在跳过
   - 写 course_enrollment(status=1) + 标记 grab_record 已落库
   - 失败重试（Kafka 重试 + 死信）
  │
  ▼
⑤ 兜底对账（定时任务）：对比 Redis 已抢数 vs MySQL 已选课数，差异回补库存或补偿落库
```

### 4.4 Redis 键设计与 Lua 要点

| Key | 类型 | 说明 |
|---|---|---|
| `grab:window:{courseId}` | String(Hash) | 抢课窗口（start/end/stock），发布时写入，TTL 至窗口结束 |
| `grab:stock:{courseId}` | String | 剩余库存，预热 = stock |
| `grab:users:{courseId}` | Set | 已抢用户集合（去重） |
| `grab:detail:{courseId}` | Hash | user → grabTime（审计/对账） |
| 分布式锁 | Redisson RLock | 库存预热/回补/对账期间防并发（Redisson 3.34.1 已在依赖中） |

Lua 脚本核心逻辑（示意）：

```lua
-- KEYS[1]=stock  KEYS[2]=users  ARGV[1]=courseId  ARGV[2]=userId
if redis.call('SISMEMBER', KEYS[2], ARGV[2]) == 1 then return 0 end   -- 已抢
local left = redis.call('DECR', KEYS[1])
if left < 0 then redis.call('INCR', KEYS[1]); return -1 end           -- 售罄
redis.call('SADD', KEYS[2], ARGV[2])
return 1                                                              -- 成功
```

### 4.5 补偿与对账

- **消息失败**：Kafka 重试 + 死信队列；消费端幂等（uk 兜底）；
- **落库失败**：定时对账任务扫描 `grab_record.status=1` 超时未落库 → 补偿落库或回补库存 + 移除 users 集合成员；
- **窗口结束**：`grab:window:{courseId}` TTL 到期自清，剩余库存回写 course.stock 冗余（可选）。

## 5. Redis 缓存体系（回答「Redis 体系化」）

### 5.1 缓存清单

| 缓存 | Key | 内容 | TTL | 失效时机 |
|---|---|---|---|---|
| 课程详情 | `course:detail:{id}` | 课程卡片+统计（选课数/抢课状态） | 30min | 发布/编辑/下架时删 |
| 章节大纲 | `course:catalog:{courseId}` | 目录树 | 30min | 目录变更时删 |
| 章节正文 | `chapter:content:{chapterId}` | 单章 markdown | 1h | 章节编辑时删 |
| 学情详情 | `learn:stats:{userId}` | 学习统计聚合（lms-learning myLearnStats 加速） | 10min | 学习行为上报后删/更新 |
| 用户基本信息 | `user:base:{userId}` | 昵称/头像/角色（供各模块 Feign 加速，替代每次查库） | 30min | 用户资料修改时删 |
| 课程积分榜 | `course:points:{courseId}` | ZSET：userId→积分 | 持久（随积分变动） | ZINCRBY 实时更新 |
| 签到状态 | `sign:last:{userId}:{courseId}` | 上次签到日期 | 随签到更新 | 签到后更新 |

### 5.2 缓存一致性策略

- **Cache-Aside + 主动失效**：写操作（发布/编辑/签到/学习上报）成功后主动删 key；
- **可选事件失效**：跨服务读缓存（如 lms-course 读 user:base）由数据源模块（lms-user）删 key，或发 `cache-invalid` Kafka 事件；
- 抢课库存/积分榜等**强一致数据不落普通缓存**，直接用 Redis 原子结构（DECR/ZINCRBY）。

## 6. 积分体系增强（lms-learning）

### 6.1 积分类型扩展（PointsType）

| 枚举 | value | 积分 | 触发点 | course_id |
|---|---|---|---|---|
| SIGN_IN | 1 | 5 | 课程页签到（改为课程维度） | 必填 |
| LEARN | 2 | 2 | 首次学习课次（保留） | 可填 |
| READ_CHAPTER | 6 | 2 | 首次阅读某章节正文（新增） | 必填 |
| EXAM | 7 | 5 | 完成章节练习/课程测验（新增） | 必填 |
| QUESTION/ANSWER/ACCEPTED | 3/4/5 | 3/5/10 | 保留（全局） | 空 |

- `points_record` 增加 **`course_id`**（空=全局流水，非空=课程内流水）；
- 发放积分时：落库流水 + `ZINCRBY course:points:{courseId} userId points`（双写，ZSET 为实时榜加速，流水为权威）；
- 阅读章节积分幂等：Redis Set `read:chapters:{userId}:{courseId}` 记录已读章节，防重复发放。

### 6.2 课程实时积分榜（ZSET，回答「右侧实时积分排名」）

- 结构：`course:points:{courseId}` → member=userId，score=课程内积分合计；
- 查询：`ZREVRANGE course:points:{courseId} 0 N-1 WITHSCORES`（TopN，秒级）；
- 我的排名：`ZREVRANK` + `ZSCORE`；
- 冷数据兜底：榜单 key 不存在时（如首次）回源 MySQL `SUM(points) GROUP BY user_id` 重建；
- 学生端课程详情右侧展示 Top10 + 我的排名；老师端可看全榜。

### 6.3 课程页签到业务（回答「判断今天是今天还是下一天」）

- `sign_in` 增加 **`course_id`**，唯一键 `uk(user_id, course_id, sign_date)`（迁移：旧数据 course_id=0 视为全局历史）；
- **日期边界业务**（Redis + MySQL 双写）：

```
签到时：
  last = GET sign:last:{userId}:{courseId}          -- 上次签到日期（yyyy-MM-dd）
  today = LocalDate.now()
  if last == today → 已签到，拒绝（幂等）              -- 「今天」边界
  else if last == today-1 → 连续签到 streak+1         -- 「下一天」边界
  else → 重新开始 streak=1
  SET sign:last:{userId}:{courseId} today            -- 更新缓存
  落库 sign_in(user_id, course_id, sign_date)         -- uk 防并发
  发放 SIGN_IN 积分（ZINCRBY + 流水）
```

- 前端入口：仅在**课程详情页**暴露签到按钮（学生已拥有该课程才可签）；签到成功提示「连续签到 N 天」。

| Kafka 消费延迟/丢失 | 落库不一致 | 生产者 ack、消费重试 + 死信、定时对账兜底 |
| 缓存一致性（课程详情/用户信息） | 脏读 | Cache-Aside 主动失效 + 事件失效；对账任务兜底 |
| ZSET 与流水漂移 | 榜单不准 | 流水为权威，ZSET 可重建；定时对账 |
| 签到并发（同一天双请求） | 重复积分 | uk(user,course,date) + DuplicateKeyException 兜底（沿用 0.1 模式） |
| 大章节 markdown 拖慢列表 | 大纲页变慢 | 目录/正文分表，大纲页不查 content |
| Text-to-SQL 注入/误执行 | 数据安全 | 只读数据源 + SELECT 白名单 + LIMIT + 超时熔断 + 审计日志 |
| 课程正文同步知识库量大 | RAG 延迟 | 异步管道（KB 已有 ingest 异步），按章同步 |

## 14. 质量检查清单（对齐技能包）

- [ ] **链路追踪**：controller 入口记录 traceId，抢课全链路（grab→Kafka→course）可追踪；
- [ ] **幂等**：抢课落库（uk）、签到（uk+日期）、阅读积分（Set）全部幂等；
- [ ] **工具实用性**：新增 AI 工具均有真实数据源，无空壳；管道节点可端到端调通；
- [ ] **降级**：Feign 失败有 FallbackFactory（沿用 UserClient 模式）；缓存穿透有兜底（榜单回源重建）；
- [ ] **安全**：Text-to-SQL 只读 + 白名单 + 限流；抢课接口防刷（窗口 + 去重）；
- [ ] **性能**：大纲/正文分表查询无 N+1；积分榜 ZSET O(logN)；
- [ ] **可观测**：Kafka 消息、对账任务、缓存命中率有日志/指标。
