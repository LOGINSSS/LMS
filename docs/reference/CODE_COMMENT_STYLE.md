# 代码注释规范（code-comment-style）

> 本仓库**所有模块的代码注释**统一遵循 `code-comment-style` 业务注释风格。
> 新增/修改代码时必须按本文档注释，提交前对照「自查清单」逐项检查。
> 技能包源：`C:\Users\24638\.dsh\skills\code-comment-style\`（个人注释风格沉淀，长期有效）。

## 一句话原则

> 注释 = 给下一个读代码的人讲**业务故事**：
> 实体类说清「它是什么」，工具类说清「它是干什么的、什么时候用」，
> 服务方法按业务步骤编号讲「先做什么、再做什么、为什么」，
> controller 只留门面、不逐行注释。

## 三条铁律

1. **服务层业务步骤拆解式注释**：方法体按业务动作切步骤，编号用层级数字
   `1.` → `1.1` → `1.1.1` 逐层递进；并列/分支选项用简单序号 `1. 2. 3.`；
   同一方法内编号唯一且递增。格式：`//1. <业务动作>：<为什么这么做 / 这一步的产出是什么>`
2. **实体类、工具类必须重注释**：类级 Javadoc 讲清「是什么 / 干什么 / 什么时候用」，
   实体字段逐字段注释业务含义（单位、关联表、枚举取值必须写）。
3. **controller 只留门面**：不逐行、不解释实现；仅非显而易见接口（幂等、限流、特殊约定）补一句。

## 分层注释强度

| 层级 | 强度 | 内容 |
|---|---|---|
| 实体 / PO / DTO / VO / Query | ★★★★★ | 类级 Javadoc + 每个字段注释 |
| 工具类 / Utils / 组件 / Config | ★★★★★ | 类级 Javadoc：用途 + 适用场景 + 使用方式 |
| 枚举 / 常量 | ★★★★☆ | 每个枚举值 / 常量注释业务含义（Redis key 注明格式、TTL 单位） |
| Service | ★★★★☆ | 方法 Javadoc（业务背景/参数/返回/异常）+ 方法体步骤编号注释 |
| Mapper / DAO | ★★★☆☆ | 复杂 SQL 注释业务意图；简单 CRUD 可省 |
| Controller | ★☆☆☆☆ | 类级职责一句话 + 非显而易见接口一句话 |
| 配置文件 / 启动类 | ★★☆☆☆ | 关键配置项说明用途，其余从简 |

## 格式硬性要求

- Javadoc 一律**纯文本，禁用 HTML 标签**（`<p>`/`<ul>`/`<li>`/`<br>` 一律不写）；
  分段用空行（单独一行 ` *`），列点用 `1. 2. 3.` 或 `-`。
- 统一**中文**注释：业务名词用中文，技术名词保留英文（Redis、MQ、Feign、JWT）。
- 代码能自明处（`return result;`、简单 getter/setter）可省注释。
- `@author` 写自己的署名或留空，不保留模板/教程代码的原作者名。
- 保障机制（幂等/唯一索引/锁/MQ 重试）必须声明「靠什么兜底」：
  `// 【保障机制】一人一单：DB 唯一索引 uk_xxx + DuplicateKeyException 捕获`

## 常用补充注释

- `// 【设计决策】为什么这么写、权衡了什么、参数为什么是这个值`
- `// 【保障机制】幂等/唯一索引/锁兜底声明`
- `// 注意：此处必须加锁，防止并发重复...`
- `// 边界：id 为空时直接返回，不做缓存查询`

## 自查清单（提交前逐项过）

- [ ] 注释无 HTML 标签，分段用空行、列点用编号
- [ ] 实体类/工具类有类级 Javadoc，字段有业务含义注释
- [ ] Service 方法体按 `//N. 业务动作：为什么/产出` 拆步骤，编号唯一递增，≤7 步
- [ ] 参数/返回值注释是业务含义（写「店铺ID」而非「Long id」）
- [ ] 幂等/锁/唯一索引等保障机制声明了兜底方式
- [ ] controller 方法体内零注释
- [ ] 注释与代码一致（改代码必须同步改注释）
