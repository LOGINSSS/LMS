# AgentScope 邀请制专家 Agent 项目总结（对话整理）

> 本文档是围绕 **AgentScope `invite_agent` 邀请制多 Agent** 项目现状与演进方向的复盘整理，
> 与本仓库 `PERSONAL_AGENT_SPEC.md`（个人 Agent 体系与三层记忆编排规范）互为参照：后者讲邀请制的正向设计，本文聚焦其工程局限与外围加固路线。

## 一、项目现状

- 技术底座：**AgentScope invite_agent 邀请制多 Agent**
- 设计模式：**业务微服务 ↔ 专家 Agent 1:1 映射**
- 架构流程：用户输入 →【主 Agent】根据任务语义，通过 `invite_agent` 邀请对应业务专家 Agent 加入会话房间；专家 Agent 被邀请后，调用自身封装的业务库/业务方法执行业务逻辑（例如 ExamAgent 做生成试卷）；执行完毕返回结果，可 remove_agent 退出会话。
- 当前缺失：**没有独立 Coordinator、没有 Plan-Mode、没有统一前置路由分发、没有统一功能检查**。
- 专家 Agent 特性：专家 Agent 偏向被动 Worker，被邀请才干活，**专家不会再主动向外 invite 其他 Agent**。

> 心智优势：邀请制非常贴近现实"开会邀请专家"，开发者理解成本低；天然适配微服务存量系统，专家可以跨进程部署。

## 二、当前架构核心局限性（原生裸邀请制带来的风险）

> 注意：不是 AgentScope 邀请制本身有 bug，是**裸用底层通信原语，缺少外围管控层**带来的工程风险。

### 1. 主 Agent（LLM）拥有无约束邀请权，全靠 prompt 软约束

主 Agent 是大模型驱动，可以自由输出 `invite_agent("xxx")`。

- 幻觉风险：业务上下文不需要 A 专家，但主 Agent 幻觉邀请高危专家 Agent；
- **没有确定性代码拦截屏障**，仅靠 prompt 约束，不能做到 100% 拦截。
- 一旦邀请高危写操作专家，会直接触发业务写库，造成生产事故。

### 2. 安全、权限校验散落在各个专家 Agent 内部

没有全局统一安全网关：

- 鉴权、高危操作确认、参数校验分散写在每一个专家 Agent 代码内；
- 容易出现某个专家遗漏校验，出现漏洞；
- 没有统一 HITL 机制，高危动作全部依赖 Agent 内部 prompt 自己询问用户。

### 3. 规划与执行耦合，缺少两阶段隔离（没有 Plan-Mode）

主 Agent 一边拆解任务，一边直接邀请专家执行真实业务变更：

- 没有只读规划阶段输出方案给人确认，再执行；
- 规划一旦出错，直接落地业务变更，缺少缓冲回退窗口。

### 4. 缺少统一会话生命周期管控

原生 invite 只是通信原语，缺少：

- 子 Agent 最大嵌套深度、会话最大 turn 轮次、token 预算、防无限循环；
- 没有统一任务板 TaskSystem，子任务状态、上下文压缩需要业务自己手写；
- 故障排查困难：没有统一层埋点 Trace，出问题只能看原始会话消息。

### 5. Agent 与业务微服务强 1:1 耦合

新增一个微服务，就要新增一个专家 Agent 类：

- 很难做到同一个底层业务能力，在不同会话做工具白名单裁剪；
- Agent 外壳和业务逻辑绑定，不利于能力复用。

### 6. 缺少外层迭代闭环（Loop-Engineering）

现在是：调用专家拿到结果直接结束。

- 没有「结果校验 - 不达标携带反馈重试 - 超限升级人工」的外层循环；
- 如果业务需要产出物校验修正（如试卷生成），无法自动迭代收敛。

> **区分概念**
>
> 1. **ReAct 内环**：每个 Agent 内部的思考-行动-观察最小循环（已有）
> 2. **Harness（管控护栏）**：管控单次执行的安全、权限、invite 拦截（缺失）
> 3. **Loop-Engineering 循环工程**：外层迭代、校验、重试、停止条件（缺失，按需引入）

## 三、后续演进方向（不推翻现有邀请制，增量加固）

> 核心原则：**不废掉 invite_agent 邀请制这个清晰的底层原语，在外围增加管控，管控收敛在会话全局，不要给每一个专家 Agent 都套全套 Harness**。
> 专家 Agent 只是薄业务外壳，只保留业务鉴权、入参校验兜底。专家不会向外发起 invite，因此专家自身不需要完整 Harness。

### 方向 A：轻量最小改造（优先推荐，改动最小，适合当前业务）

只实现**会话全局轻量 Harness 拦截层**，整个会话只一份，不侵入专家 Agent。

1. **增加 onBeforeAgentInvite 前置钩子（Host 拦截层）**
   在真正调用 `invite_agent()` 之前执行确定性代码校验：
   - 校验子 Agent 嵌套深度，防止死循环；
   - 会话维度 Agent 白名单：当前会话上下文，允许邀请哪些专家；LLM 幻觉输出不在白名单内的 Agent，直接拒绝，返回让主 Agent 重规划；
   - 高危标记：对会写库、修改业务数据的专家 Agent 标记高危，邀请前强制触发**硬编码 HITL 人工确认**（不是靠 Agent 内部 prompt 询问）。
2. 基础会话兜底：会话最大 turn、最大 token，超限终止会话。
3. 专家 Agent 保持薄壳：仅保留业务鉴权、入参校验作为第二道兜底，不需要 Plan-Mode、任务板。
4. 可观测：增加 Trace 埋点，记录：谁发起邀请、邀请哪个 Agent、触发原因、HITL 结果。

> 适用场景：内部系统、输入不完全开放；高危动作不多。
> 安全底线：**安全靠 Host 确定性代码，prompt 仅降低概率，不作为安全屏障**。

### 方向 B：进一步增强（业务走向面向外部开放用户，风险更高时叠加）

在轻量 Harness 基础上，可选追加组件，按需开启，不是必须全部上。

1. **启用轻量 Plan-Mode 规划执行两阶段**
   - 规划阶段：主 Agent 仅输出"计划要邀请哪些专家、做什么子任务"，**禁止真实执行 invite_agent**；
   - 用户人工确认计划之后，才进入执行阶段真正发起邀请。
   > 注意：Plan-Mode 属于 LLM 侧约束，存在被绕过可能，**不能替代 Host 的硬拦截层，只是增加一道缓冲**。
2. **按需引入 Loop-Engineering 外层大循环**
   针对需要产出物校验迭代的业务（生成试卷、报告等）：
   - 外层 Loop 封装总目标；内部复用现有的整套邀请制多 Agent；
   - 独立校验器（尽量不用干活 Agent 自评）校验结果是否达标；
   - 不达标携带缺陷反馈重新驱动主 Agent 规划 + 邀请专家；设置最大迭代次数，超限升级 HITL 人工介入。
   > 注意：Loop 不会修复单次执行的安全问题，依赖底层 Harness 已经做好防护；否则 Loop 会把错误反复放大。
3. **长远解耦**：把专家 Agent 内部业务逻辑抽离为独立工具/服务接口，Agent 只做薄薄消息外壳，缓解 Agent 与微服务 1:1 强耦合问题。

### ❌ 不推荐的演进路线

1. 全盘推翻邀请制，重写成 CC 风格 Coordinator + fork 子 Worker 模式：心智完全切换，改造成本巨大，现有微服务专家 Agent 资产浪费；邀请制本身是很好的原语，只是缺外围护栏。
2. 给每一个专家 Agent 都完整部署一套 Harness/Plan-Mode：管控逻辑分散，大量重复代码，规则不一致，维护爆炸。

## 四、关键概念对比（面试可直接输出）

| 模块 | 定位 | 在本项目中现状 |
|---|---|---|
| invite_agent 邀请制 | 底层多 Agent 会话通信原语，实现专家加入/退出会话 | ✅ 在用，心智清晰，保留 |
| ReAct 内环 | Agent 内部思考-工具-观察最小循环 | ✅ 已有 |
| 全局 Harness 工程 | 外围管控护栏：invite 前置拦截、白名单、高危 HITL、会话生命周期 | ❌ 缺失，优先补轻量版本；管控收敛在会话全局，不下沉到每个专家 |
| Plan-Mode | 规划-执行两阶段隔离，只读规划缓冲 | 🟡 可选增强，高风险业务开启；不能替代硬拦截 |
| Loop-Engineering 循环工程 | 外层迭代闭环：目标、校验、重试、停止、超限升级人工 | 🟡 按需引入，仅用于需要迭代修正产出物的场景 |

> **重要认知**：
> Harness 不是"每个 Agent 都要实例化的重型类"，是一套管控思想；
> Loop、Plan-Mode 都是上层可选组件；**确定性 Host 拦截才是安全底线**。

## 五、面试口述精简版（项目复盘回答）

> "我们项目基于 AgentScope 的 invite_agent 邀请制多 Agent，采用微服务与专家 Agent 一一映射的架构。主 Agent 根据任务邀请对应专家 Agent 进入会话执行业务，专家 Agent 大多是被动 worker，不会再发起新的邀请。这套方案优势是贴合微服务存量，业务心智清晰。
>
> 但裸用底层邀请原语存在明显局限：主 Agent 拥有不受约束的邀请能力，全靠 prompt 软约束，存在 LLM 幻觉错误邀请高危专家、直接触发业务写操作的风险；权限校验分散在各个专家 Agent；没有规划执行两阶段隔离；缺少统一会话生命周期管控；也没有外层的校验重试 Loop 闭环。
>
> 所以我们不会推翻邀请制这套原语，采用增量加固思路：优先实现会话全局的轻量 Harness，在 invite_agent 执行之前增加 Host 拦截钩子，做嵌套深度校验、会话维度 Agent 白名单，高危专家邀请强制硬编码 HITL 确认；专家 Agent 保持薄外壳，只做业务鉴权入参兜底。
> 如果后续业务面向外部开放，会再按需叠加 Plan-Mode 做规划-执行隔离；对于需要迭代修正产出物的场景，引入 Loop-Engineering 外层迭代闭环。安全底线始终放在确定性代码，prompt 只作为概率降低手段，不作为安全屏障。"
